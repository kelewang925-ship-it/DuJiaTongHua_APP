# 工坊图片请求超时 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 工坊保存相册的真实图片请求超时后可继续操作，数据不丢失且可明确重试。

**Architecture:** 在相册写入前的私有decodedImage函数内设置15秒截止，复用UI.busy的错误与按钮恢复。超时拒绝本次等待并清理图片来源和计时器，旧请求迟到不恢复已失败的写入路径。

**Tech Stack:** 原生JavaScript、Image.decode、Promise、浏览器计时器、现有Playwright/Python本地验证。

**Spec:** design-html/prototype/ACCEPTANCE_REQUIREMENTS.md第10/37项，docs/html-development-standards.md交互与状态要求，以及原提示词Error State的“请求超时”。

## 已复现与原需求

原提示词 Error State 明确包含“请求超时”及可继续操作。当前工坊相册导出在存储之前等待原生 `Image.decode()`，缺少应用层上限；真实本地 HTTP 图片响应挂起后，超过15秒按钮仍处于“保存图片中…”且禁用。baseline/album-timeout 的三案例实际进程73490退出1：超时／迟到响应两项失败，超时前真实响应并保存的对照通过。两项失败均发生于 deadline-check，已观察到真实请求且存储保持，没有替换图片解码Promise或时钟。

首轮关闭仍挂起的Route产生Playwright收尾取消日志，已保存原测试脚本；仅在记录结果后补充Route清理，不改动三个案例的业务断言。

## 决定及影响范围

在 `assets/prototype-workshop-store.js::decodedImage` 增加15秒截止。超时中止当前图片来源并拒绝本次等待，通过已有 `UI.busy` 错误／finally路径显示“图片准备超时，请重试保存”、恢复保存按钮。超时发生在相册写入之前，原作品、原照片及候选数据保持。用户明确再次保存才开始新请求；旧响应迟到不得写入。

静态全局搜索只有 `prototype-workshop.js` 中完成作品页面的 `#save` 调用 `W.album`。公共 `album` 的来源核对、快照／并发检查、相册去重及存储逻辑继续复用；仅修改其私有图片准备函数，正常页面结构与样式保持。
